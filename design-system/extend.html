扩展协议

遇到组件库里没有的需求，按这六步推导、实现和登记。设计师和 Agent 走同一套流程，产出的结果才能回到系统里，供下一次复用。

待确认草案。决策表里的数值都来自当前的 tokens.css 和原型源码；流程本身和停止条件还需要确认。

流程总览

  1. 理解需求

    用一句话写下：用户要完成什么任务、涉及什么内容、出现在哪种页面模式里、数据量大概在什么范围（0 条、1 条、很多、很长）。

  2. 查找并选择复用级别

    在 library/catalog.json 里按意图和 summary 搜索，不要只搜名称。然后按下表决定复用到什么程度。

  3. 用决策表推导样式

    颜色、表面、圆角、字号和间距都从语义角色推出来，不凭感觉取值。

  4. 列出状态矩阵

    交互状态、数据状态、内容压力和不同环境，逐项写出来。

  5. 写组件契约

    按 catalog 的结构写清用途、禁忌、结构、属性、行为、来源和每个形态的状态标记。

  6. 实现、登记与验收

    在原型里实现，登记进组件库，运行同步脚本，然后按清单验收。

第 2 步：选择复用级别

从上往下检查，第一条成立的就是答案。级别越靠前，系统越稳定。

情况做法登记方式例子
现有组件完全满足直接复用，只换内容不用登记新频道列表直接用图文内容卡
结构相同，只差一个属性或状态给现有组件加一个形态在原组件的 variants 里新增，状态标“建议”内容卡要显示活动日期
用几个现有组件就能拼出来组合使用，不新建类名登记为“组合示例”作者卡加关注按钮
以上都不满足新建组件新增 catalog 条目，必须走完第 3 到 6 步全新的交互形态

第 3 步：决策表

先确定元素的角色，再查表取 Token。组件里只写语义变量，不写原始色值。

颜色角色

想表达使用不要
区域里的主要行动--action-primary 背景，配 --text-on-action（ds-button primary）蓝色按钮；同一区域放多个黑色按钮
次要行动ds-button secondary / ghost在列表的每一项里都放黑色主按钮
当前位置、已选中--accent-surface / --accent-text黑色背景
链接、可点的文字--text-link，悬停用 --accent-text只靠下划线或粗体
进度--progress-track / --progress-fill，同时配文字说明绿色进度条
成功、已完成--status-success / -bg / -text蓝色
提醒、限制--status-warning / -bg / -text黄色收藏色
失败、危险操作--status-danger / -bg / -text点赞红 --reaction-liked
内容分类--badge-{green|red|blue|amber|purple|yellow}-bg/-text用状态色表示分类
文字层级--text-heading → -primary → -secondary → -tertiary用透明度调灰
键盘焦点--focus-ring 轮廓去掉 outline 却不提供替代反馈

表面与层级

层Token效果
画布--surface-canvas无边框、无阴影
主内容卡、工作空间--surface-default，--radius-card无阴影
次级区块（侧栏块、控件底色）--surface-secondary / --surface-hover无阴影
悬停相邻色阶 --article-surface-*-hover / --feed-surface-neutral-hover不加黑色遮罩
菜单、弹层--surface-default + --shadow-popover可以用 78% 玻璃 + 24px 模糊，必须有实色回退
浮动控件、滚动边缘62% 玻璃 + 16px 模糊不覆盖整段正文

圆角、字号与间距

角色取值Token / 来源

筛选容器、弹层20px--radius-lg
嵌套面板、图片、提示12px--radius-md

胶囊、头像、标签全圆角--radius-full
页面标题30 / 42px / 500；手机 24 / 32px--type-page / --type-title-lg
分区说明13 / 22px / 400--type-small
正文14px / 1.65--type-body / --type-body-lh

动态数字等宽数字font-variant-numeric: tabular-nums

表里没有的取值不能直接用，先按停止条件登记。

第 4 步：状态矩阵

逐项写出这个组件在每种情况下的样子。确实不适用的，写明“不适用”和原因，不要直接省略。

  • 交互：默认、悬停、按下、键盘焦点、选中、禁用
  • 加载：骨架屏的结构要和最终内容对应
  • 空：说明原因，给出下一步行动
  • 错误：原位显示，提供恢复路径，不只用轻提示
  • 内容压力：长标题、长姓名、没有图片、标签过多（折叠成 +N）
  • 宽度：1000px 以上、760px、390px
  • 键盘：Tab 顺序、Enter / Space、Esc 退出
  • 读屏：可访问名称；状态不只靠颜色表达
  • 动效：遵循 prefers-reduced-motion
  • 深色：只用语义变量；整体验收待进行

第 5 步：组件契约

沿用 library/catalog.json 的字段结构。下面带 // 新增 的字段是建议补充的推理信息，便于下一个 Agent 理解这个组件为什么这样设计。

{
  "id": "event-card",
  "group": "内容与交流",
  "name": "活动卡",
  "en": "Event card",
  "summary": "一句话写清何时使用。",
  "variants": [ { "label": "可报名", "html": "…", "status": "建议" } ],
  "usage": ["何时使用"],
  "avoid": "何时不要使用，以及应该改用什么",
  "anatomy": ["结构部件"],
  "props": [["属性", "取值", "作用"]],
  "behavior": "键盘与交互约定",
  "source": ["实现文件"],
  "size": "关键尺寸",
  "tokens": ["--radius-card", "--status-success-bg"],   // 新增：用到的语义 Token
  "extends": "content-card",                            // 新增：派生自哪个组件
  "alternatives": ["forum-post"],                       // 新增：容易混淆的相邻组件
  "principles": ["01", "05"]                            // 新增：主要依据的原则
}

状态标记：已有 表示原型里已经实现；组合示例 表示由现有组件拼出的文档示例；基础样式 表示只有样式、没有业务；建议 表示推导出来、还没确认。不能把“建议”写成“已有”。

第 6 步：登记与验收

  1. 在 html-pages/prototype/assets/ 的对应文件里实现，只使用语义变量。
  2. 在 design-system/scripts/build-library.py 里用 item(...) 登记组件，用 v(...) 登记形态。
  3. 在项目根目录依次运行： 
    python3 design-system/scripts/sync-tokens.py
node design-system/scripts/extract-specimens.cjs
python3 design-system/scripts/build-library.py
  4. 同步更新 COMPONENTS.md 的索引。
  5. 打开 library-audit.html，在 1000px 和 390px 下检查选择器、图片和溢出，再人工检查键盘和长文本。
  6. 在 DISCUSSION.md 的“待确认”里记一笔，说明新增了什么、依据哪些原则。

何时停下来问人

遇到下面任何一种情况，不要自行决定后直接上线。先在 DISCUSSION.md 的“待确认”里写下需求、方案和理由，契约里的状态标为“建议”。

情况为什么要问
需要新的颜色，或者表外的字号、圆角、间距会改变整个系统的比例和语义
需要改变现有组件的外观或行为会影响所有已经使用它的页面
引入新的交互方式（拖拽、手势、全屏弹窗、自动播放）原则里没有覆盖的取舍
和 DISCUSSION.md 里“已确认”的规则冲突已确认的规则只能由人修改
原则之间冲突，按优先级仍然无法判断说明原则本身需要补充

示例：活动报名卡

完整走一遍六步。活动页目前只有设计好的空状态，这个示例演示的是推导过程，不代表已经实现。

1. 理解需求

成员在活动列表里浏览近期活动，并决定是否报名。内容包括封面、标题、时间、地点或线上、名额和报名状态。页面属于内容流模式。数据量：0 条（已有空状态）到几十条；标题和地点可能很长。

2. 选择复用级别

搜索“卡片、封面、列表”，命中图文内容卡：封面、标题、元信息的结构相同，只多了时间、名额和报名状态，所以属于第二级：给现有组件加形态，不新建组件。论坛帖子卡以文字讨论为主，排除。

3. 推导样式

部件推导结果
卡片容器沿用内容卡（原则 07）--radius-card，相邻色阶悬停
时间与地点属于元信息，不是行动12px，--text-secondary，日期用等宽数字
报名按钮列表里每张卡都有，不能每张都用黑色主按钮（原则 02）ds-button secondary sm；黑色主按钮留给详情页
“已报名”表达的是结果，不是选中（原则 02）--status-success-bg/-text 标签，不用蓝色
“名额将满”提醒--status-warning-bg/-text
“已结束”不可操作按钮隐藏，标签用 --status-info 的灰色，卡片仍可以进入回顾

4. 状态矩阵

  • 可报名、已报名、名额将满、已满、已结束
  • 报名中：按钮 aria-busy，防止重复提交
  • 报名失败：卡片内原位提示，可以重试
  • 加载：复用图文卡骨架
  • 空：沿用活动页现有空状态
  • 没有封面：退回纯文字色卡
  • 标题和地点很长：完整换行，不截断
  • 390px：单列，按钮命中区域至少 44px

5. 契约要点

id: content-card 新增 5 个 variants，status: "建议"；tokens 列出上面用到的状态 Token；principles: ["01","02","05"]。

6. 需要问人的地方

“已结束”的活动是隐藏还是保留用于回顾？报名是否需要确认弹窗？这两点属于业务和交互取舍，记入 DISCUSSION.md 待确认。
