设计原则

组件库里没有现成答案时，用这些原则推出答案。每条原则都写了理由、现有系统里的证据、可以直接问自己的判断问题，以及反例。

待确认草案。根据 2026-09-24 原型、SYSTEM.md 和已确认的讨论记录归纳。确认之前仅作推理参考，不作为强制规则。

怎么使用

  1. 先通读一遍。弄清这套系统在取舍时看重什么，比记住数值更重要。
  2. 新设计中的每个决定都要过一遍“判断问题”。能用语义 Token 或现有组件回答的，就不要发明新值。
  3. 原则互相冲突时，按本页末尾的优先级处理。仍然无法判断时，按扩展协议记录下来，交给人确认。

七条原则

01

内容是主角，界面退后

界面只负责把内容组织清楚，不和内容抢注意力。

为什么

成员来岛上是为了发现工具、读经验、学课程。真实的封面、标题、代码和截图本身信息已经很多，再加界面装饰只会把它们冲淡。

系统中的体现
  • #F7F7F9 画布上放白色阅读表面
  • 内容卡不强求等高，用瀑布流 channel-masonry
  • 真实配图保留来源，品牌标志不统一染色
  • 不用生成封面，也不用随意的装饰渐变
判断问题

把这个装饰、容器或颜色去掉，内容会更难理解吗？不会的话就去掉。

反例

给每张卡片垫一张渐变底图；为了网格整齐把标题截成一行；把第三方工具的 logo 染成品牌蓝。

02

颜色各有职责：黑色负责行动，蓝色负责定位

每种颜色只承担一种语义。黑色是“请你去做”；蓝色说明“你在哪、选中了什么、还差多少”；状态色只用来表达结果。

为什么

页面上同时有大量内容和操作。颜色的语义只有一种，用户扫一眼就能分清哪里可以点、什么被选中了、哪里出了问题。Agent 也可以按语义选 Token，不必凭“好看”去猜。

系统中的体现
  • 主操作 --action-primary 是黑色
  • --accent-* 蓝色阶用于选中、链接、进度和文件夹插画
  • 成功用独立的绿色 --status-success-*，不借用蓝色
  • 点赞红、收藏黄只在阅读互动中使用
判断问题

这个颜色是在请用户行动，还是在说明状态？如果是状态，是哪一种？有没有对应的语义 Token？

反例

用蓝色做主按钮；用蓝色表示“已完成”；把点赞红当成错误色；在组件里直接写原始色值。

03

用表面和留白区分层级，不靠阴影和描边

先用表面色阶和间距区分层级。只有浮在内容之上的元素才加阴影或玻璃效果。

为什么

阅读界面里的元素很密，阴影和线条一叠加就成了噪音。相邻色阶既能分出层级，界面也能保持安静。

系统中的体现
  • 画布 → 白色主卡（24px 圆角）
  • 悬停时换成相邻色阶，例如 --article-surface-blue-hover，不加黑色遮罩
  • 阴影只有三级：--shadow-sm 小控件、--shadow-md 提示与轻提示、--shadow-lg 菜单、弹层与导览
  • 玻璃只用在筛选胶囊（62% 表面色 + 16px 模糊）、弹层（78% + 24px）和滚动边缘
判断问题

这个元素浮在内容之上吗？如果没有，就只用表面色和间距来区分。

反例

给普通卡片加投影；在整段正文上铺玻璃；悬停时整张卡片变暗。

04

形状随角色缩放

圆角和间距由元素在层级里的角色决定，不逐个元素去调。

为什么

比例关系统一了，新组件自然就和旧组件协调，Agent 也能直接推出数值，不用凭感觉。

系统中的体现
  • 主容器和主要卡片 24px
  • 筛选容器和弹层 20px
  • 小控件 4 / 6 / 8px，胶囊全圆角
  • 间距以 4px 为基数；已知例外是外壳间隔 6px 和胶囊内边距 3px
判断问题

这个元素是容器、浮层、控件还是胶囊？去决策表里取值。如果需要表里没有的数值，先登记为例外，等人确认。

反例

新卡片随手写 12px 圆角；凭感觉写 10px、14px 这样的间距。

05

每个状态都要被设计

一个界面在加载中、没有内容、出错、文字很长、窄屏和只用键盘操作时，都要有明确的样子，才算做完。

为什么

社区内容是真实用户发的，数量和长度都无法预测；专栏、活动这类板块还会长期没有内容。如果没有设计这些状态，用户会把空白当成还在加载或者出了错。

系统中的体现
  • 骨架屏的结构对应将要出现的内容（page-loading.js 分别为图文卡、帖子、榜单行生成）
  • 空状态说明原因，并给出下一步，例如“写第一篇帖子”
  • 加载失败时，在主内容区原位显示，可以重试（已确认的主导航规则）
  • 列表到底时显示“已经看完全部内容”
判断问题

没有数据、数据很多、文字很长、加载失败、只用键盘时，这个界面分别长什么样？

反例

所有异常都显示同一个“暂无数据”；用转圈代替骨架屏；错误只用一闪而过的轻提示告知。

06

记住用户所在的位置

筛选条件、频道、滚动位置和来源页面都要保留，用户返回时能回到原处。

为什么

用户会在列表和详情之间来回切换。丢了位置，阅读节奏就被打断了。

系统中的体现
  • 路由和筛选状态写在 hash 里，可以分享，刷新后能恢复
  • 从详情返回时回到来源频道、列表或搜索结果，而不是统一跳回首页
  • 点击主导航后立即切换选中状态，不等内容加载完
判断问题

用户离开再回来、刷新页面，或者把链接发给别人时，能回到同一个状态吗？

反例

返回按钮固定跳回首页；筛选条件只存在内存里，一刷新就没了。

07

先复用再扩展，扩展要有依据

优先使用已有组件和语义 Token。必须新建时，从原则和决策规则推导出来，并登记回系统。

为什么

设计系统的价值在于一致。每一个没有登记的新样式，都会变成下一个 Agent 学错的参考。

系统中的体现
  • 50 个组件族在 library/catalog.json 中都有契约
  • 每个形态都标了状态：已有、组合示例或基础样式
判断问题

组件库里有没有能满足八成需求的组件？新加的东西写进契约了吗？

反例

复制一个组件，改几个数值，另起一个类名；引入新颜色却不定义语义 Token。

冲突时的优先级

两条原则给出的答案相反时，按下面的顺序取舍。排在前面的优先。

顺序关注点对应原则例子
1可用、可访问，状态完整05、06点赞和收藏不能只靠颜色区分，要加 aria-pressed 或状态文字，哪怕界面因此多一点信息。
2内容可读01标题很长时完整换行，不为了卡片对齐截成一行。
3系统一致02、03、04、07新组件即使局部看起来更好看，也要用现有的圆角和颜色角色。
4局部视觉表现—只在前三项都满足以后再调整。

下一步：遇到新需求时，按扩展协议把这些原则落到具体的 Token 和状态上。
